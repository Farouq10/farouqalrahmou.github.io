# Firestore backend for the scientific library

**Status:** implementation committed, NOT deployed and NOT connected to a live Firebase project.
**Frontend:** index.html is deliberately untouched. No visible content, layout or URL changes.

## What this contains

- backend/client.js: ready-to-import browser Firestore service. Public paginated
  listings, published/draft access, create/edit/archive/delete, Google sign-in,
  optimistic edit-conflict checks, and loaded-page text search.
- backend/model.mjs: reusable schema and input validation.
- firestore.rules: deny-by-default security, public read of *published* items only,
  custom-claim-protected writes, field/type/size checks, immutable ownership
  and creation times, server-generated timestamps, 25-document list cap.
- firestore.indexes.json: indexes for published listing by kind/subject/date.
- backend/tests/: ordinary-unit and Firestore-emulator rules tests.
- .github/workflows/firebase-checks.yml: CI checks, no deploy permissions.
- backend/scripts/set-admin.mjs: local, privileged administrator-claim setup.
- firebase.json: Firestore rules/indexes and local emulators, no Firebase Hosting.

## Start a no-cost Firebase project (manual, once)

1. In Firebase Console create a project using the Spark plan. Register a **Web app**.
2. Enable **Cloud Firestore (Standard edition)** in a region appropriate for UK readers.
   Select locked-down/production mode. Deploy this repository's rules before adding data.
3. Enable **Firebase Authentication > Google**. Add the GitHub Pages domain
   to Authentication > Settings > Authorised domains.
4. On a trusted computer install Node.js 22+ and run: npm install
5. Test locally: npm test (uses Java 21 and downloads the Firestore emulator).
6. Authenticate to Firebase CLI: npx firebase login
7. Review target project carefully and deploy only database configuration:
   npx firebase deploy --project YOUR_PROJECT_ID --only firestore:rules,firestore:indexes

**IMPORTANT:** Deployment to an existing Firestore project *replaces that
project's Firestore rules/index definitions*. Inspect the target before deploying.
Never use a project that already hosts an unrelated application.

## Assign administrator rights

Sign into the registered app once using Google Authentication, then find the
user's Firebase Authentication UID. On a trusted machine, authorise yourself
using Google Application Default Credentials with permissions to manage
Firebase Authentication users. Then run:

npm run admin -- --project YOUR_PROJECT_ID --uid YOUR_AUTH_UID --action grant --confirm YOUR_PROJECT_ID

This adds a secure custom claim (siteAdmin=true). Sign out/in to refresh it.
Only a privileged Admin SDK environment can assign such a claim. Merely knowing
a project's public Firebase web configuration never gives write access.
You can revoke access with --action revoke (and confirm project ID).

**Do not commit** service account credentials, any private keys, tokens,
passwords, or an admin SDK initialisation script containing credentials.
The script above uses Application Default Credentials, not a checked-in key.

## Wire into the unchanged visual design (later, when authorised)

Once a Firebase project exists, pass its *public web-app config* to
createLibraryBackend() imported from /backend/client.js. The script is
intentionally **not** imported by index.html yet, so the existing website looks
and behaves exactly as it did before this commit.

Example (for a future JS module, not presently injected into the page):

import { createLibraryBackend } from "./backend/client.js";
const api = createLibraryBackend(firebaseConfig);
const firstPage = await api.listPublished({ subject: "mathematics", size: 20 });
// Render firstPage.items with textContent (never innerHTML).
// Pass firstPage.cursor back to listPublished({ cursor: firstPage.cursor }).

The Firebase JS imports use version-pinned official gstatic modules. Database
metadata is safe to expose in browser code; the rules and custom claims secure
the database. Do not treat API keys as passwords.

## Record shape: libraryEntries/{autoGeneratedId}

{
  schemaVersion: 1,
  kind: "note" | "resource" | "project",
  subject: "mathematics" | "physics" | "chemistry" |
           "engineering" | "computing" | "other",
  status: "draft" | "published" | "archived",
  title: string (1..160 characters),
  summary: string (0..2000),
  body: string (0..20000), // plain text, do not render unescaped HTML
  url: "" | "https://...",
  tags: string[] (at most 8, each 1..40 characters),
  ownerUid: string, // assigned by authenticated admin on creation
  createdAt: Firestore timestamp, // server timestamp at creation
  updatedAt: Firestore timestamp  // server timestamp on each write
}

No user comments, public uploads, public writes, Cloud Functions, Cloud Storage,
paid backups, Firebase Hosting, or third-party API keys are included.

## Operating considerations

- Firestore Spark free quota: 1 GiB data, 50k reads/day, 20k writes/day,
  20k deletes/day, 10 GiB outbound per month (one free database per project).
  Avoid huge lists and excessive polling. Pages default to 20, maximum 25.
- Firestore has no native general full-text search. searchLoadedPage() filters
  *only the page already fetched*. It does not search your full database.
- Admin edit/delete calls require the previous updatedAt timestamp and use
  transactions to reject stale edits. Archive rather than hard-delete ordinarily.
- Data content is plain text; public viewers should see only published items.
  Never store personal secrets or copyrighted full-text books without rights.
- CI tests run against a local emulator, not production. No automatic deployment.
- No automated backups or billing alerts have been configured; managed Firestore
  backups / point-in-time recovery are not part of the free Spark allowance.
- Consider downloading periodic exports of important writing separately before
  treating this as your only copy. A database is not a backup.
